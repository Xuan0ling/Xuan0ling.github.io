Default Arguments

  • Parameters with default values must be at the end of the parameter list
  • Default values must be in the declaration (header) when using separate compilation

Function Overloading

Same function name, different parameter list (number or type). Return type is not part of the signature.

Function signature consists of:

  1. Function name
  2. Number of parameters
  3. Type of parameters
  4. Sequence of parameters

Static vs. Dynamic Polymorphism

  • Function/Operator overloading = static polymorphism (resolved at compile time)
  • Virtual functions = dynamic polymorphism (resolved at runtime)

Part 3: Design Patterns

Design patterns are well-thought-out, reusable solutions to common problems in object-oriented design.

Iterator Pattern

Provide a uniform interface for traversing different data structures.

Decorator Pattern

Dynamically add behaviour to objects without modifying their class.

Four components:

  1. Abstract Base Class — pure virtual methods only
  2. Concrete Component — core object with base implementation
  3. Abstract Decorator — inherits from base, holds a pointer to base
  4. Concrete Decorators — extend with extra fields/behaviour

Example: Pizza Ordering

Observer Pattern

Let a Subject notify multiple Observers when its state changes.

Execution flow:

  1. Concrete Subject is changed
  2. notifyObservers() is called
  3. notify() is called on each Observer
  4. Each Observer calls getState() and updates itself

Example: Twitter

Factory Method Pattern

Define an interface for creating objects, but let subclasses decide which class to instantiate.

Template Method Pattern (Non-Virtual Idiom)

Define the skeleton of an algorithm in a base class, deferring some steps to subclasses.

Non-Virtual Idiom (NVI)

Rules:

  1. Public methods should be non-virtual
  2. Virtual methods should be private or protected
  3. Exception: destructor should be public virtual

Benefits:

  • Add pre/post code to execute() without changing the public interface
  • Compiler can optimize away the extra function call

Coupling & Cohesion

Coupling — extent to which modules depend on each other:

  • Low (desirable): simple communication via parameters/results
  • High (avoid): modules share access to each other’s implementation

Cohesion — how closely related are the parts of a module:

  • Low (avoid): unrelated parts grouped together
  • High (desirable): all parts cooperate toward a single purpose

Goal: low coupling + high cohesion

Forward Declaration

Note: Forward declaration is not allowed for inheritance or non-pointer fields.

Single Responsibility Principle (SRP)

Each class should have exactly one reason to change.

Model View Controller (MVC)

Component Responsibility
Model data and domain logic
View output and display
Controller input and control flow

Exception Safety

Three levels of guarantees:

Guarantee Meaning
Basic Program in valid but unspecified state; no leaks or corruption
Strong Program state is as if the function was never called
NoThrow Function never throws and always succeeds

RAII — Resource Acquisition is Initialization

Constructor acquires the resource. Destructor releases it.

If an exception is thrown, the destructor for all stack-allocated objects is called during stack unwinding — guaranteeing cleanup.

Smart Pointers <memory>

unique_ptr

Owns a heap-allocated object. Deleted when the unique_ptr goes out of scope.

  • Copy is disabled — would cause double delete
  • Move transfers ownership

Ownership semantics:

Type Meaning
unique_ptr<T> owns the memory
raw pointer T* borrows — does not free
moving unique_ptr transfers ownership

shared_ptr

Multiple shared_ptrs can point to the same object. Uses reference counting.

PImpl Idiom (Pointer to Implementation)

Provides the strong guarantee by swapping pointers atomically.

noexcept

Tag a function to indicate it will never throw. Required for vector to use move semantics during resize:

If a noexcept function does throw, std::terminate() is called immediately.

Casting

static_cast

Compile-time cast with well-defined semantics. Use when you are certain of the type.

const_cast

Remove const from a type.

dynamic_cast

Runtime-checked downcast. Returns nullptr (for pointers) or throws std::bad_cast (for references) if the cast fails. Requires at least one virtual method.

Good use: operator= with polymorphic types.
Bad use: long if-else chains checking subtypes — prefer virtual methods instead.

Polymorphic Assignment

  • If operator= is non-virtual → partial assignment (only Book fields copied)
  • If operator= is virtual → mixed assignment (may assign a Comic to a Text)
